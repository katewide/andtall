> В andtall активны webhook тегирования и массовая установка тегов по дате закрытия на /ai-test. Описанные ниже закрытие задач и старый preview отключены; актуальное поведение см. README.md.

# Теги type, product и object

При закрытии задачи Gemma по-прежнему формирует `SUMMARY` и `TITLE` по исходному промпту. В этот же запрос включаются инструкции из `task-tagging.md`: один ответ содержит SUMMARY, TITLE и технический блок AI_TAGS. Перед записью комментария AI_TAGS удаляется; TITLE записывается в UF_TASK_TITLE, SUMMARY — в UF_TASK_SUMMARY, разобранные теги — в TAGS.

Справочник разрешенных значений находится в `task-taxonomy.json`.

Варианты названий конфигураций и их приведение к каноническим тегам заданы в `product_normalization` файла `task-taxonomy.json`.

## Что записывается

Пример:

```text
type: консультация
product: ЗУП
product: БП
object: документ_СчетНаОплату
```

Тег `type:` может быть только один. Тегов `product:` и `object:` может быть несколько. Другие, в том числе ручные, теги задачи сохраняются.

Если Gemma не смогла доказательно определить категорию, существующие управляемые теги этой категории не удаляются.

## Настройки

```env
TASK_TAGGING_ENABLED=true
TASK_TAG_FIELD_NAME=tags
```

- `TASK_TAGGING_ENABLED=false` полностью отключает добавление инструкций и запись тегов.
- `TASK_TAG_FIELD_NAME` — имя поля в API-адаптере. По умолчанию используется `tags`.

## Безопасная проверка

В уже работающем сервисе откройте:

```text
/ai-test
```

Режим preview вызывает Gemma, но не пишет комментарий, SUMMARY или теги в задачу. Страница показывает теги AI и итоговый набор тегов.

API работает асинхронно:
- `POST /ai-preview?taskId=<ID>` сразу возвращает HTTP 202 с `job_id` и `status: "running"`. GET сохранён как альтернативный запуск.
- `GET /ai-preview/status?jobId=<job_id>` возвращает `running`, `completed` с полем `result` или `failed` с полем `error`.
- Повторный запуск той же задачи во время анализа возвращает существующий job_id. Одновременно допускаются две проверки; превышение лимита возвращает 429.
- Общий лимит анализа — 180 секунд, бюджет медиа — 45 секунд. Если медиа не успели обработаться, анализ продолжается по доступным данным с предупреждением.
- Результаты хранятся в памяти одного процесса до 10 минут, максимум 20 записей. Перезапуск их удаляет; отсутствующий результат возвращает 404. Для нескольких экземпляров сервиса требуется общее хранилище заданий или привязка запросов к одному экземпляру.

В поле `result` завершённого задания проверьте:

```json
{
  "tag_classification": {
    "found": true,
    "type": "консультация",
    "products": ["зуп"],
    "objects": ["отчет"],
    "object_names": [{"type": "отчет", "name": "АнализЗарплаты"}]
  },
  "task_tags": ["type: консультация", "product: ЗУП", "object: отчет_АнализЗарплаты"],
  "task_tags_would_be_updated": true
}
```

После проверки preview можно закрыть отдельную тестовую задачу и убедиться, что теги добавились в Bitrix24.

## Защита от повторного запуска

Обновление тегов само вызывает `ONTASKUPDATE`. `server.js` запоминает свои обновления на 10 минут и не запускает повторный анализ для такого события.

## Объекты работы

Справочник `objects` содержит: `отчет`, `расширение`, `регистр`, `документ`, `обработка`, `справочник`, `печатная форма`, `обмен`, `роль`. AI выбирает только объекты с подтверждённым конкретным наименованием; случайные упоминания и инструменты проверки не учитываются.

Непустой проверенный список `object_names` заменяет прежние теги `object:`. При отсутствии корректных имён новые объектные теги не создаются; прежние теги этой категории сохраняются. Список `objects` без имён не используется для генерации тегов. Ручные теги без управляемых префиксов сохраняются. В `/ai-test` новые теги отображаются вместе с `type:` и `product:`.

## Имена объектов

Если точное техническое имя явно указано в исходных материалах, AI возвращает его отдельно в `object_names`:

```json
{
  "objects": ["документ", "расширение"],
  "object_names": [
    {"type": "документ", "name": "СчетНаОплату"},
    {"type": "расширение", "name": "ЭЛРОС_Доработки"}
  ]
}
```

Создаются только теги с конкретными именами:

```text
object: документ_СчетНаОплату
object: расширение_ЭЛРОС_Доработки
```

Вид объекта остаётся в нижнем регистре; написание имени сохраняется. Без подтверждённого имени новый тег не создаётся. Старые ответы с одним списком `objects` не создают объектных тегов. Непустой проверенный список имён заменяет всю категорию `object:`; если имён нет, прежние теги сохраняются. Массовое удаление старых общих тегов не выполняется. `/ai-test` показывает только сгенерированные именные теги, а в итоговом наборе — также сохраняемые прежние теги.

## Единый формат и выбор продукта

Новые объектные теги имеют формат `object: вид_ТехническоеИмя`, например `object: роль_РольOData`. Код принимает имена из букв, цифр и подчёркиваний, начинающиеся с буквы или подчёркивания. Пробелы и пунктуация не удаляются автоматически: такое имя отклоняется. Подтверждение того, что это именно техническое имя, возложено на промпт; одна проверка формата не доказывает его существование.

Пользовательские названия и описания вроде «выплата зарплаты сотрудникам» не создают теги. Если имён нет, прежние объектные теги сохраняются; массовой миграции старых тегов нет. При новой непустой классификации категория `object:` заменяется тегами нового формата.

По согласованному правилу проекта АУСН как предмет работы или консультации означает `product: БП`. `product: 1С-отчетность` выбирается только при подтверждённой работе с самим сервисом, а не по упоминанию налоговой, отчётов или АУСН. Правило реализовано в промпте классификации.

## Сохранение TITLE, SUMMARY и тегов

- `UF_TASK_TITLE` (`ufTaskTitle`) получает TITLE из ответа AI. Существующее исключение для группы «только SUMMARY» сохраняется.
- `UF_TASK_SUMMARY` (`ufTaskSummary`) получает содержимое блока SUMMARY без заголовка SUMMARY, TITLE и AI_TAGS. Поле должно быть заранее создано в Битрикс24 как строковое пользовательское поле задачи.
- После PATCH SUMMARY задача перечитывается: несовпадение значения считается ошибкой. Теги записываются только при непустом сохранённом SUMMARY, совпадающем со значением на момент запуска. Если SUMMARY не выделен из ответа, старое поле не очищается и теги этого запуска не записываются.
- Перед PATCH тегов ещё раз читается задача для получения актуальных тегов и SUMMARY. После PATCH теги также перечитываются и сравниваются с ожидаемыми. Ошибка или неприменённое изменение не кэшируются как успех.
- Прежний непустой SUMMARY обновляется новым итогом; прежние управляемые теги обновляются по действующим правилам категорий, ручные сохраняются.

`ONTASKUPDATE` с изменением `UF_TASK_SUMMARY` запускает отдельную фоновую классификацию по исходным материалам задачи, включая доступные изображения и аудио. Внешнее заполнение/изменение SUMMARY таким образом обновляет теги без повторной записи полей и комментария. TITLE сам по себе больше не запускает теги. Очистка SUMMARY не запускает AI и не удаляет теги.

Одновременные события одной задачи объединяются. Успешно обработанный SUMMARY кэшируется на 10 минут в памяти; изменённый текст обрабатывается снова. После перезапуска кэш пуст. Событие собственного сохранения ожидает обработки закрытия и использует уже применённый результат. События тегов не запускают эту ветку. Ошибки допускают повторную попытку при следующем событии.

Ограничение фоновой обработки — 180 секунд. Диагностика: `/debug` → `lastTaskSummaryTags`. Preview `/ai-test` не пишет данные; показывает `generated_summary`, `task_summary_field`, `task_summary_field_would_be_updated`, а также планируемые теги. Исторические ключи `summary_field*` в preview по-прежнему относятся к TITLE; новые ключи `task_summary_field*` относятся к `UF_TASK_SUMMARY`.

Автоматический обход старых задач при деплое не запускается. Удалённые тесты с живым порталом не выполнялись; локальные регрессионные проверки: `node --test tests/title-tags.test.cjs`.

## Оформление тегов

После префиксов `type:`, `product:` и `object:` ставится один пробел. Сокращения продуктов отображаются как БП, ЗУП, УТ, КА, ERP, ДО, ЭДО, КЭДО, УНФ; остальные — 1С-отчетность и Розница. В JSON-классификации канонические ключи остаются в нижнем регистре. Сервер и `/ai-test` используют один форматтер. Старые теги заменяются новым форматом при обработке соответствующей категории; массового переименования нет.


### Источники классификации

SUMMARY, TITLE и теги определяются одним запросом AI по исходному названию, описанию, человеческим комментариям, записям времени и доступным результатам обработки изображений и аудио. Родительская задача используется как контекст. Закрытие, ai-test и обработчик UF_TASK_SUMMARY используют общий сбор материалов и единый промпт. Обработчик внешнего изменения SUMMARY применяет только теги из ответа; собственное сохранение SUMMARY не запускает повторную классификацию после успешной записи тегов.

UF_TASK_SUMMARY — только условие записи тегов и защита от устаревшего результата при параллельном изменении. Его содержимое, UF_TASK_TITLE, прежние теги и сгенерированные AI-комментарии не передаются классификатору. Теги извлекаются из того же ответа, что SUMMARY/TITLE, но определяются по исходным материалам, а не по сжатому итогу. Поддерживаемые медиа в предпросмотре и обработчике SUMMARY имеют общий ограниченный бюджет; недоступные медиа могут быть пропущены.


### СЭДО и исправление сбоев после обновления

Восстановление типовой работы ЗУП, включая установку готовых исправляющих патчей для устранения конкретного сбоя, относится к `консультация`. Если основной работой является обновление релиза, применяется `обновление`; изменение собственного кода относится к `разработка`.

СЭДО в ЗУП не даёт отдельного продукта ЭДО: для задачи о восстановлении СЭДО после обновления загрузкой 14 патчей ожидаются `type: консультация` и `product: ЗУП`. Самостоятельная работа с 1С-ЭДО может подтвердить дополнительный продукт ЭДО. Сопоставление сокращений выполняется по полному обозначению, без совпадений по подстроке.

Это правила AI-промпта; качество классификации проверяется на исходных материалах через ai-test. Существующие теги задач автоматически при деплое не пересчитываются.
